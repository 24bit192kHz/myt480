# 2026-11-02: session pollers without a fork per tick

Idle with the screen locked (the normal state on battery), the T480 started
13 programs per second (401 execs in 30 s, counted with the kernel proc
connector, `PROC_EVENT_EXEC`). None of it was work; all of it was polling:

| Poller | Every | Programs per tick |
|---|---|---|
| `bw-screen boot`, waiting for the boot lock to go | 0.25 s | `pgrep -x slock` (a full /proc scan) |
| `monitor.sh watch` | 2 s | `cat` per DRM connector (5), `sleep` |
| `lock-powersave` | 2 s | `pgrep`, `cat`, `iw`, `awk`, `sleep` |

Changes:

- `src/t480-watch` (Rust, no dependencies, 350 KB, 2.3 MB RSS) replaces
  `lock-powersave` (same name through a symlink, so run.sh's singleton test still
  matches) and the loop of `monitor.sh watch` (the script `exec`s it when it is
  installed and keeps its own loop as the fallback; the apply logic stays in
  the script). Both read /proc and sysfs directly and start `xset`, `iw` or
  `monitor.sh` only on a change; the Wi-Fi power-save state is re-read every
  30 s instead of every 2 s.
- `bw-screen boot` waits on the locker's pidfd instead of polling pgrep.
  Zombies are skipped (here and in t480-watch): an exited, unreaped locker's
  pidfd is readable at once, and the first test version spun on one.

Result: 136 execs in 30 s, the rest are bar.sh (every 5 s), cron jobs once a
minute and the kernel asking for `net-pf-16-proto-9` (NETLINK_AUDIT, not built)
on each PAM login. Old versions: `~/t480-build/work/pre-t480-watch/` on the
T480. Rollback: put those back and restart the three processes.
