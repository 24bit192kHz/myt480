# 2026-10-09 evening: the audit deployed, the gaps closed, sleep tested

Follow-up to the audit published on `testing` (`research/2026-10-09-t480/`). Done
over SSH from the workstation; the owner was away. Nothing was flashed: no change
in the audit calls for a firmware build before the lid-wake result below.

## What the audit had left on the laptop, and what it had missed

Installed and verified byte for byte against the branch: the fan-watchdog
`thermald-t480`, `gpu-power`/`prime-run` with `rtd3 1`, `igpu-run`, the Bitwarden
desktop override. Not installed: the later `gpu-power.c` fixes (`d69ed06`).

Three things the audit did not see:

- **Bitwarden is not started from the desktop file.** The session script runs
  `bw-screen boot`, and the hibernate-later hook restarts it the same way, so the
  override would have changed nothing after a reboot and the MX150 would have
  stayed in D0 on AC. `bw-screen` now launches it through `igpu-run`.
- **The NVIDIA sleep override of 2026-10-05 had never run.** elogind 257 executes
  `/usr/lib/elogind/system-sleep` first and masks `/etc` by file name, the
  opposite of the systemd convention the override assumed. No `nvidia-sleep` line
  had ever reached syslog. The package file is removed and kept out by
  `NoExtract = usr/lib/elogind/system-sleep/nvidia` in `pacman.conf`.
- **The audit installed straight into `/usr/local` and `/etc`**, bypassing
  `syswork`: four files sat uncommitted in `/usr/local`'s git, the sources under
  `~/systemagent/src` were still the old ones, and a stale `syswork` worktree
  (`gpu-auto`, Sept 30) held the old `gpu-power` and `prime-run`. All committed,
  synced and dropped now; everything below went through `syswork`.

## The lid-wake experiment

The EC report (`research/2026-10-09-t480/10-ec-firmware-and-lid-wake.md`) traces a
retained flag, set from EC RAM byte `0x01` bit 6 (`BTPC` in Lenovo's DSDT, which
never writes it on this model), that enables lid detection in the EC's S4/S5
state and turns a lid open into the power-button pulse that already wakes S3. The
2026-10-08 verdict "impossible on stock too" rested on the host side (what
Lenovo's SMM and ACPI write); it shows that stock never enables the path, not
that the EC lacks it.

The hook sets the bit before every hibernate and clears it after the resume
(`touch /etc/elogind/no-lid-wake-s4` disables it). Setting and clearing survive
an S4 cycle without side effects.

**It works.** At 19:22 and 19:23 the owner hibernated from the session menu,
closed the lid and opened it: the laptop powered on and resumed both times.
`cbmem`: `PM1_STS: WAK PWRBTN`, `prev_sleep_state 4`; the only RTC alarm was the
stale one from the earlier test (pending: no). The EC's lid path drives the same
PWRBTN# line as the button, so this is exactly the expected signature, and the
firmware cannot tell the two apart; the owner's hands were on the lid, not the
button. The hook is the feature; no firmware change is needed. Bitwarden,
restarted by `bw-screen` after each resume, now runs through `igpu-run`: no
process holds `/dev/nvidia*` and the GPU sits in D3cold while it is open.

Seen in the log at each session-menu hibernate, tonight and on 2026-10-08:
`bitwarden-app ... trap invalid opcode`, the Chromium `CHECK` abort when
`hibernate-safe` kills Bitwarden. Old, harmless, not touched.

## Mistake of the evening

To see why the NVIDIA hook was silent, the hook was run by hand with `pre
suspend`. That executed the real `nvidia-sleep.sh suspend`: console on VT 63,
driver in its suspend state. Undone a minute later with `nvidia-sleep.sh resume`
(VT 1 back, X intact, no Xid). Run hooks with `sh -n` or a dry verb, never with
the live arguments.

## 2026-10-10, 02:00–03:00: the early-init trust boundary closed

The audit's top finding: `init.c` loaded the TPM master key whenever `/boot/t480`
existed, before anything checked that the root is the expected LUKS2 volume, and
a plain root's init then ran with the key in its keyring. A plain disk swapped in
next to the real `/boot` would have got the key on a clean boot (a valid
hibernation image resumes the real system first).

The fix, kernel 7.2.8-8: the key is released only for a LUKS2 root, or when the
kernel command line carries the bare word `t480.provision`, which the
conversion's check boot needs on the still plain disk. The word can be trusted
because the command line is part of the GRUB configuration coreboot measures
into PCR 2, and only the GRUB shell or entry editor behind the GRUB password can
add a word the default entry lacks. On a plain root without the word the log
says "plain root: TPM key left sealed". A plain root next to an encrypted swap
now asks the passphrase for the swap. The `kmk.next` one-shot path is unchanged.

Checks, all on the workstation:

- The published offline fixture, now two runs: production command line with no
  master load, provisioning word with it.
- The QEMU rehearsal with the new init as an external initramfs over the 7.2.8-7
  image and a software TPM: a new stage boots sealed keys on a plain root with the
  production command line and finds the key sealed and PCR 8 extended; then the
  harness adds the word and the old sequence follows: check boot released,
  conversion, TPM boot, hibernate and resume, one-shot blob, firmware change,
  passphrase, rekey. (A stage that changes the command line must power off, not
  reboot: the harness restarts QEMU only then.)
- Kernel 7.2.8-8 built from the kit's `PKGBUILD` with the new init embedded. The
  configuration differs from 7.2.8-7 only in the compiler version lines (clang
  23.1.1 now).

Installed on the laptop at 02:26 with `pacman -U` of both packages: the hooks
copied the kernel to `/boot/vmlinuz-linux-t480`, signed it with the firmware's
key (good signature) and built the NVIDIA DKMS module for 7.2.8-8. 7.2.8-7 stays
beside it as `vmlinuz-linux-t480-7.2.8-7.bak` with its signature (bootable from
the GRUB shell), and its module directory was put back for the running kernel
until the reboot. Booted at 02:37 (warm reboot on the owner's go, back in 13 s):
`root opened, swap opened, TPM key released, 240 ms`, the three keys in root's
keyring, GPU in D3cold with the driver loaded, fan daemon, watchdog and X up, no

## 2026-10-10 afternoon: a hibernation on the stock kernel that never came back

The owner tried the stock `linux` entry at 03:27, closed the lid at 03:38 and
opened it at 15:27. The stock kernel suspended for an hour and wrote its image
at 04:38. On the wake GRUB started its default, linux-t480, which cannot load
another kernel's image (`PM: hibernation: Failed to load image, recovering`): a
fresh boot, the stock session lost. Nothing else broke: swap was clean again, the
EC lid-wake bit was back at 0x05, all three keys were in root's keyring.

- `local.d/stock-kernel-sleep.start`: on any kernel that is not `*-t480` it puts
  runtime drop-ins in `/run/elogind` (lid = plain suspend, hibernation and
  suspend-then-hibernate refused) and reloads elogind (SIGHUP; tested, same PID).
  `20-hibernate-later` stays unarmed there (`/run/t480-no-hibernate`).
- `90-battwatch-marks`: battwatch's sleep marks live in `/run`, which went with
  the image, so the daemon filed the 11.8 h as an unclean power loss. The hook now
  also keeps `/var/lib/battwatch/hibernate.pending` from `pre hibernate` to `post
  hibernate`; the daemon (battwatch, not part of this kit) reads it on a boot
  change and files a lost image as such, with the sleep before it split off.
- Measured anyway from battwatch's samples: BAT1 53.41 -> 49.56 Wh over 11 h 49 m
  (1 h S3 + 10 h 49 m S4), 0.33 W on average; BAT0 did not move.
- The stock kernel's S3 resume also logged `xhci_hcd 0000:06:00.0: Host halt
  failed, -19` with a warning trace, and correctable AER errors on 00:1d.0: the
  Thunderbolt controller had powered its idle USB host down during the sleep and
  the kernel removed the vanished device. linux-t480 never shows the TB xHCI
  without a device attached either. Not a fault; nothing to change.
