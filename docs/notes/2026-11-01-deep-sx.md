# 2026-11-01: hibernation drain and Deep Sx (C61)

**Symptom.** Measured by battwatch, every hibernation since 2026-10-06 drew 0.27-0.29 W
(10-28: 97 h took BAT1 from 21.2 to 3.7 Wh at 0.18 W), while a full power-off drew
0.09-0.19 W.

**Cause.** The PCH power-gating policies were all zero under coreboot (PWRMBASE 0xfe000000:
`S3_PWRGATE_POL` 0x28, `S4_PWRGATE_POL` 0x2c, `S5_PWRGATE_POL` 0x30, `DSX_CFG` 0x34), so
the suspend well stayed powered in S3, S4 and S5. Lenovo's N24ET74P (probe dumps
`stock-full-*/inteltool-p.txt`, on AC and battery alike) sets 0x3, 0x3, 0xc000 and 0x1: Deep
Sx in every sleep state on AC and battery, LAN_WAKE# kept as a wake pin.

**Fix.** Patch 0030 sets the same values in the T480 devicetree (`deep_s3_enable_ac/dc`,
`deep_s5_enable_ac/dc`, which also covers S4, `deep_sx_config = DSX_EN_LAN_WAKE_PIN`).
WAKE# stays disabled through `PCIEXPWAK_DIS`, as before. The ROM differs from C60 only in
the ramstage, the romstage and postcar (devicetree) and the version string.

**Flashed as C61, 2026-11-01 23:36** (FMAP + COREBOOT, one-shot TPM blob, warm reboot).
Checked afterwards: registers 0x3/0x3/0xc000/0x1, firmware time 0.58 s, disk key re-sealed
to the new PCR 2, MX150 present (D3cold with the driver).
- S3 with an RTC wake: coreboot logged `Enabling Deep S3`, `prev_sleep_state 3`,
  `PM1_STS: WAK RTC`, all 24 PCI functions back, watchdog re-armed.
- Hibernation with an RTC wake: `prev_sleep_state 4`, image restored, lid-wake hook set and
  cleared EC 0x01 bit 6, watchdog re-armed.

**Remote end-to-end audit, 2026-11-01 23:40-23:58 (on AC, lid open).**
- 5 S3 cycles with RTC wakes: 5 entries, 5 exits; MX150 back in D3cold, 24 PCI functions,
  TCO watchdog active, Wi-Fi up after each; no Xid.
- Cold boot from Deep S5 by an RTC alarm (`work/coldboot.sh "" 45`): cbmem `prev_sleep_state 5`,
  `PM1_STS: WAK RTC`, MRC cache used, firmware 1.03 s, SSH up 6.5 s after power-on, disk key
  unsealed by the TPM (PCR 2 742BC24B... as after the warm boot), every service of the
  default bundle up.
- The lid-close path itself: `loginctl suspend-then-hibernate` with HibernateDelaySec=60 and a
  temporary hook arming an RTC wake for the S4 phase (both removed afterwards): S3, elogind's
  own wake, hibernate, RTC wake from S4 (`prev_sleep_state 4`), lid-wake hook armed and
  cleared, watchdog disarmed and re-armed, battwatch split it into sleep + hibernate rows.
- MX150: `nvidia-smi` wakes it (P0, PCIe gen 3), back in D3cold seconds later.
- Logs: cbmem only the known lines (no SLIC, CSE disabled); dmesg only known lines (atkbd
  "Failed to deactivate keyboard" on cold boots since October, Bluetooth -16 since October).
- CPU microcode 0xf6 = the newest release (microcode-20260925), in coreboot and the OS.
- Not possible remotely: battery drain (on AC; `charge_behaviour` offers only `auto`, no
  force-discharge), lid/keyboard/power-button wakes, WoL (no cable).

**Still to test by hand.** Lid open and keyboard wake from S3, lid open and power-button wake

## 2026-11-02: resume speed and CPU mitigations

- Resume from hibernation measured at 8.3 s from power-on to the thawed session (firmware 1.0 s,
  GRUB about 0.5 s, kernel to early init 0.85 s, TPM unseal and dm-crypt about 0.3 s, image load
  3-4 s, device restore 1.23 s with i915 0.95 s and USB up to 1.0 s). A 1.9 GB image resumed as
  fast as a 2.6 GB one.
- `10-upower-battery-heal` slept 5 s inside elogind's post hooks, which delayed every wake
  report (NetworkManager reconnect, lockers) by 5 s; the wait now runs detached.
- After the thaw the fan is in EC auto (about 2000 rpm) until thermald sets its level again
  (about 23 s); the loud fan is during the restore boot, before the session is back.
- C62 (grub.cfg: `mitigations=off` replaced by `retbleed=stuff hibernate_compression_threads=8`)
  booted with every mitigation active (meltdown PTI, MDS/MMIO clear buffers, retbleed stuffing,
  GDS/SRBDS microcode). Cost: getpid-type syscalls about -50 %, `git status` +30 %, Python
  start-up +5 %, AES unchanged. But hibernation entry HUNG twice (log ends at elogind
  "Performing sleep operation 'hibernate'", next boot `prev_sleep_state 0`, image not found),
  the second time with the owner present. The save path differs from C61 only in the
  mitigations, so one of them breaks hibernation here. Back on C61 since 2026-11-02 01:00;
  next: bisect the mitigations one build at a time, test the restore threads separately.

## 2026-11-02, night: C64 and the hibernation fixes

Done remotely between 01:00 and 02:50 with the screen off; every hang test was made
self-recovering first.

- **Why C62 hung.** A test harness (`work/hibtest.sh` on the T480) hibernates with
  elogind `HibernateMode=test_resume` (image written and restored at once, no power-off) and
  keeps a 300 s TCO running through it, so a hang in the save path ends in a TCO reset
  (`TCO_STS: SECOND_TO`) instead of a lit machine. C62 (`retbleed=stuff`) hung twice, also
  with the NVIDIA driver unloaded; C63 (`mitigations=auto`, Retbleed via IBRS) passed. So
  call-depth tracking hangs the image write on this 7.2.8 kernel. Benchmarks (median of 3,
  AC): Python start-up 0.420 s off, 0.447 s IBRS (+6 %); 5x `git status` 0.351 s -> 0.516 s
  (+47 %); getpid-style syscalls 1.67 M/s -> 0.68 M/s; AES-GCM unchanged.
- **Do not leave the TCO running into a real S4.** Tried as a hang guard (sleep-guard keeping a
  480 s TCO through the hibernation instead of disarming it); reverted.
- **Patch 0031.** After the owner's 4 s holds that night, every Deep S4 wake showed PRBTNOR
  again (cleared on each boot, back after each Deep Sx exit): the restore boot skipped the
  dGPU, asked for the boot menu, and Linux refused the image. The override now only counts
  with `prev_sleep_state` S0.
- **Early wakes from S4 on AC.** 3 of 7 hibernations on AC woke after 8-50 s with only
  `PM1_STS: WAK` (GPE0 `PME_B0`); none in 3 runs with GLAN wake off. `02-sleep-guard` now
  disarms the GbE wake for every hibernation (WoL stays armed for S3 on AC).
- **Bluetooth stall.** The Intel 8265 Bluetooth (`btusb`, usb 1-7) needed 41 s in its restore
  callback in 2 of 7 resumes, and the thaw waited for it. Plain `modprobe -r` before the
  hibernation moved the stall to the entry (35-37 s), because bt-autoconnect's paging keeps a
  connect open. New hook `04-btusb-hibernate`: soft-block hci0's own rfkill, unload btusb
  (about 0.6 s), load it again after the resume and restore the block state.
- **Result (C64 + hooks).** 4 hibernations in a row: entry 2.0 s, resume 7.4-9.4 s power-on
  to thawed session (the RTC has 1 s resolution), same session, MX150 present, Bluetooth back,
  no early wake. suspend-then-hibernate (lid path) with a 60 s delay: S3, hibernate, resume
  into the same session. Remaining long pole in the device restore: the card reader (usb 2-3,
  1.0 s, in parallel with i915 0.93 s).
